# 第3章 LLMアプリケーションの構築 — なぜこの章が必要か

# どんな現場課題に効くか

LLM を業務に組み込む段階で最初に詰まるのは、「ベタな OpenAI API 呼び出しの寄せ集め」を「テスト・観測・差し替えが効く構造」に育てる方法がわからないことです。プロンプトを少し変えるたびに動作確認に時間が溶けたり、ツール呼び出しを追加するたびに状態管理がスパゲッティになったり、というのが典型例です。本章で扱う LangGraph によるエージェントは、状態遷移を `StateGraph` として明示的に書く構造を与えることで、この「LLM を呼ぶスクリプト」と「LLM をコンポーネントにしたアプリケーション」の間を橋渡しします。

# 使わないとどうなるか

LangGraph のような骨格を入れずに、`while` ループと if 分岐でツール呼び出しを書き続けると、ツールが増えるほど条件分岐が指数的に増え、「いまどの状態か」を読み解くのに時間がかかるコードになります。さらに後続章 (4 章以降) で導入する MLflow Tracing は、`autolog` がフレームワーク (LangChain / LangGraph) のフックに依存しているため、ベタ書きの API 呼び出しではトレースの粒度が粗くなり、観測性の恩恵を得にくくなります。**3 章で骨格を入れることが、4 章以降のすべての機能を活かす前提**になっています。

# 本書の該当節と一緒に読むと良い箇所

- 本書では `StateGraph` の組み立て手順が中心ですが、`MemorySaver` (会話履歴の保存) の使い分け、`ToolNode` の挙動、エラー時の中断と復帰、といった「実運用に乗せるとき気になるポイント」までは紙面の都合で深堀りできていません。本リポジトリ `ch3/agents/langgraph/agent.py` の最終形を写経しながら、LangGraph 公式ドキュメントの State Machine セクションと Memory セクションを併読すると、「なぜこの形に収束するか」が腹落ちしやすくなります。
- 本章単独だとトレーシングの恩恵が見えないため、まず ch3 で動かしたあと、すぐ ch4 に進んで MLflow UI でトレースを眺めるのがおすすめです。「3 行追加でこれだけ見える」という体験が、LangGraph 構造を採用するモチベーションになります。
