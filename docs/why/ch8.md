# 第8章 監視と運用 — なぜこの章が必要か

# どんな現場課題に効くか

LLM アプリを本番運用に乗せた瞬間、現場では (1) 月末に突然届くプロバイダの請求書 (コストの突発増)、(2) 「最近回答がおかしい気がする」という曖昧な品質劣化の報告、(3) ユーザの「いいね / よくない」フィードバックを集めても活かせない、という 3 つの問題が出ます。本章で扱う MLflow の監視機能は、これらに対して、コスト集計・トレース上での品質監視 (継続評価)・フィードバック収集の 3 点セットを提供します。さらに OpenTelemetry エクスポートで、社内既存の APM (Datadog 等) と統合できます。

# 使わないとどうなるか

監視の仕組みを入れずに本番運用すると、(1) コストの異常 (バグでループしてトークンを浪費、特定ユーザがプロンプトインジェクションでツールを乱発、等) を月次精算まで気付けない、(2) 品質劣化の検知が「ユーザの苦情」起点になる、(3) フィードバックを集めても、どのバージョンのプロンプト・どのモデルでの会話だったかが紐付かないので学習に使えない、という事態に陥ります。本章を入れずに運用するのは「アクセスログの無い Web サイトを運用している状態」に近いので、OSS の MLflow であっても本章相当の機能は早期に導入する価値があります。

# 本書の該当節と一緒に読むと良い箇所

- 8.1 節 (トレーシングのメタデータ) は地味ですが効果が大きい節です。`session_id`、`user_id`、`request_id` などをトレースに付けておくと、(1) 「同一ユーザの会話履歴の絞り込み」、(2) 「特定リリース後のトレースだけを評価」、(3) 「外部のアクセスログとの突合」が可能になります。本書の 1 段下で運用に効く論点なので、`make tracing` を最初に動かすときに「自分のチームならどのキーを足すか」を考えながら読むのがおすすめです。
- 8.2 節 (コスト集計) のレートはプロバイダ側のドキュメントから自動的に引かれていますが、社内の特別レート (エンタープライズ契約等) には対応できません。本書の手法をベースに、社内レートの上書き表を別途持つ運用にすると、月次の請求と乖離が出にくくなります。
- 8.5 節 (OpenTelemetry エクスポート) は、社内に既に APM 基盤がある場合に大きな効果があります。逆に APM 基盤が無いチームは、まず MLflow UI 単体で運用し、規模が大きくなってから OTel に流す、の段階を踏むのが現実的です。
