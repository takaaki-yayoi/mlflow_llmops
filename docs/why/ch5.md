# 第5章 評価の仕組み — なぜこの章が必要か

# どんな現場課題に効くか

PoC で動いた LLM アプリを本番に持っていく際、最大の障壁は「変えてよい / 変えるな」の判断軸が無いことです。プロンプトをちょっと変えたとき、別の LLM に乗せ換えたとき、ツールを増やしたとき、それが「本当に良くなった」のか「別の質問では悪化している」のかを **数値で判断できない**と、改善のサイクルが個人の感覚 (vibe check) に閉じます。本章で扱う `mlflow.genai.evaluate` は、評価データセット・スコアラー・対象モデルを 3 点セットで定義し、結果を MLflow に記録することで、この「変更の良し悪しを毎回計測できる」状態を作ります。

# 使わないとどうなるか

評価基盤を持たないチームでは、リリース判断が「動作確認をした担当者が OK と言ったから」に依存し、回答品質の劣化が後から発覚する事故が起きやすくなります。特に LLM は同じプロンプトでも温度パラメータや LLM プロバイダのモデル更新で挙動が変わるため、**評価セットを継続的に回す仕組みが無いと、リグレッションが「ユーザの苦情」として可視化される**ことになります。本章を入れずに 6 章以降 (Prompt Registry のバージョン切り替え、AI Gateway の LLM 切り替え) に進んでも、変更の安全性を保証する根拠が無いため、結果として「怖くて切り替えられない」状態になります。

# 本書の該当節と一緒に読むと良い箇所

- 本書は標準スコアラー (5.4.4) → カスタムスコアラー (5.4.5) → LLM ジャッジ (5.4.6) の順で粒度を上げて解説しています。実務でいきなりカスタムスコアラーを書こうとすると挫折しやすいので、**「まず標準スコアラーで何が測れるか」を理解する** ことを優先するのが本書の意図と合っています。本リポジトリの `evaluation/02_standard_scorers.py` から順に動かすのがおすすめです。
- 5.7 節以降の応用編 (会話シミュレーション、LLM ジャッジのアライメント、サードパーティ評価ライブラリ連携) は本書冒頭で「読み飛ばし可能」と明記されています。最初は飛ばしてかまいません。「評価データが手元に少ない」「LLM ジャッジの判定が人間の感覚とずれる」といった課題に当たってから戻ってくると、各応用編の役割が腹落ちします。
- LLM ジャッジ (`make_judge`) のコストは見落とされがちです。1 サンプルの評価につき 1 回以上の LLM 呼び出しが追加で発生するため、本書 5.5-5.6 節を最初に動かすときは小さめのデータセットから始めて、コスト感を掴んでからスケールさせてください。
