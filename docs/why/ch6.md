# 第6章 Prompt Registry — なぜこの章が必要か

# どんな現場課題に効くか

LLM アプリの「ロジック」は実質的にプロンプトです。にもかかわらず、多くの現場ではプロンプトがソースコードに直書きされていて、変更履歴を Git のコミットからしか追えなかったり、A/B テストや段階的ロールアウトをしようとすると同じコードに条件分岐を生やすしかなかったり、という事態になります。本章で扱う Prompt Registry は、プロンプトを「バージョン管理対象のリソース」として MLflow に登録し、エイリアス (`production`、`staging` 等) を介してコードと疎結合に運用できる仕組みを提供します。これにより、**プロンプト改修をデプロイから切り離す**ことができます。

# 使わないとどうなるか

プロンプトをソースコードに埋め込んだまま運用すると、(1) プロンプト 1 行の修正にもアプリのデプロイが必要になり、PMやドメインエキスパートが触れない、(2) 過去のバージョンに戻したいとき git の特定コミットを掘り起こす必要がある、(3) 評価結果と「どのプロンプトのバージョンか」の紐付けが手動になる、といった摩擦が生じます。Prompt Registry を入れることで、エイリアスを切り替えるだけでロールバック・カナリア・チーム内レビューがフローに乗ります。

# 本書の該当節と一緒に読むと良い箇所

- 6.2 節 (登録・バージョン更新・エイリアス) は土台です。実運用ではこの 3 つだけでも価値が大きいので、本リポジトリの `make register` → `make version` → `make alias` を一度通しで実行し、MLflow UI の Prompts タブでバージョンとエイリアスの関係を視覚的に把握してください。
- 6.2.6 (モデルパラメータの紐付け) と 6.2.7 (構造化出力) は、「プロンプトと推論設定をセットで管理する」設計思想を実感するセクションです。`temperature` や `response_format` のような「プロンプトと一緒にバージョン管理したいパラメータ」を切り出すクセがつきます。
- 6.3.4 (MetaPrompt / GEPA) は API コストが大きい応用編です。本書 5 章の評価基盤がきちんと整っていることが前提になります。本リポジトリの `make optimize-gepa` を本番想定のデータセットで回すと、数千回の LLM 呼び出しが発生する場合があります。最初は小さなデータセットでアルゴリズムの挙動を観察してください。
