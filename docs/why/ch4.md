# 第4章 可観測性の確保 ――トレーシングの導入 — なぜこの章が必要か

# どんな現場課題に効くか

LLM アプリは「動いた」「動かなかった」の二値で済まず、「期待した回答に近いか」「ツール呼び出しが妥当だったか」「想定外のレイテンシが出ていないか」を継続的に把握する必要があります。普通のバックエンド API ならログレベルを調整するだけで足りますが、LLM の場合は「どのプロンプトでどの中間出力が出てどう判断したか」までを span のツリーとして残さないと、不具合再現が極端に難しくなります。本章で導入する MLflow Tracing は、この「LLM 用に最適化された構造化ログ」を `autolog` の 1 行で導入できる仕組みです。

# 使わないとどうなるか

トレーシングを入れずに「とりあえず print デバッグ」「ログに requests のレスポンスを丸ごと書き出す」で進めると、本番でユーザから「変な回答が返った」と報告が来たとき、再現に必要な情報 (使われたツール、ツールの戻り値、その時の中間プロンプト) が散逸して特定不能になります。さらに、5 章以降の評価機能は **トレースを入力として動く**ため、トレースが無いと評価パイプラインが組めません。「監視と評価が連動していること」は MLflow GenAI 全体の設計思想であり、4 章はそのハブになります。

# 使わないとどうなるか (もうひとつ)

OpenTelemetry や Datadog APM 等で代用しようとすると、LLM アプリ固有の意味付け (どこが LLM 呼び出しで、どこがツール呼び出しか、その usage tokens は何か) を自前で計装する必要があります。本書 8 章で扱うトークン消費・コスト集計の仕組みも、トレースに `usage` 情報がぶら下がっていることが前提になっているため、**MLflow Tracing で取った形にしておくと後段機能が全部繋がる**のが大きな利点です。

# 本書の該当節と一緒に読むと良い箇所

- 本章のコード差分は ch3 から見て 4 行 (import を含む) のみです。「4 行で何が嬉しいか」を体感するため、まず ch3 を一度動かし、その後 ch4 で同じ会話をして MLflow UI の Traces タブを眺める、という順で進めると効果が伝わります。
- 本書では autolog ベースの自動計装が中心ですが、「ツール内の特定の処理にもう一段の span を切りたい」「外部 API 呼び出しを span 化したい」といった要件には `@mlflow.trace` デコレータでの手動計装が必要です (4.6 節)。本リポジトリには未収録ですが、リスト4.5 のとおり `process_query()` にデコレータを足すか、`agents/langgraph/tools/web_search.py` の Exa API 呼び出し部分に足すと、「自前計装と autolog の併用」を試せます。未収録コードの一覧は [ch4/CHAPTER_NOTES.md](../../ch4/CHAPTER_NOTES.md) を参照してください。
