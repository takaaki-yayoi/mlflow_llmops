# 第7章 サービングとデプロイメント / AI Gateway — なぜこの章が必要か

# どんな現場課題に効くか

LLM アプリを本番に乗せるとき、「とりあえず Flask で包んで Docker に入れて Kubernetes にデプロイ」では片付かない論点が 2 つあります。**1 つはエージェントとサービングの境界**で、ローカルで動いていた LangGraph エージェントを、外部から呼び出せる形 (REST/Streaming) にしつつ、評価パイプラインからも同じ実体を呼べる構造にする必要があります。**もう 1 つは複数 LLM プロバイダの管理**で、OpenAI / Anthropic / Google / オンプレ LLM を切り替え可能にし、コスト・レート・キーをアプリ層から剥がしたくなります。本章で扱う Agent Server と AI Gateway は、それぞれの論点に対する MLflow 流の答えです。

# 使わないとどうなるか

Agent Server を使わない場合、Flask / FastAPI のラッパを自前で書くことになり、(1) MLflow Tracing との連携を再実装する必要、(2) 評価 (5 章) で同じエージェントを呼び出すコードが二重化、(3) `@invoke` ベースの統一インターフェースが無いため、後から streaming やマルチエージェント (9.3 節 ResponsesAgent) に移行しづらい、といった摩擦が出ます。

AI Gateway を使わない場合は、(1) プロバイダ SDK ごとにアプリを書き分ける、(2) コストがアプリのログから算出できず月次精算が紐解けない、(3) レート制限のロジックがアプリ側に散る、(4) API キーが各アプリの環境変数に分散して棚卸しが大変、という痛みが現場に蓄積します。星 5 のレビューが「コスト管理・レート制限・プロバイダ切り替えといった、いざ運用に乗せるとなった時に必ず必要になる仕組みが整理されている」と書いているのは、まさにこの痛みを先回りで吸収できることへの評価です。

# 本書の該当節と一緒に読むと良い箇所

- 7.4 節 (AI Gateway) は **MLflow のバージョンによって構成が大きく異なる** セクションです。MLflow 3.10 以降は Tracking Server に統合された新方式 (`http://localhost:5000/gateway/...`) ですが、3.9.0 以下では別プロセスで起動する Legacy 方式を使うことになります。本リポジトリは互換性のため `gateway/gateway_config.yaml` の Legacy 方式も提供しています。詳細は [ch7/CHAPTER_NOTES.md](../../ch7/CHAPTER_NOTES.md) を参照してください。
- 7.5 節 (本番デプロイメント) では Dockerfile / K8s マニフェスト / Databricks Agent Framework の 3 ルートが紹介されます。**まずどの環境にデプロイするかを決めてから読む**と効率的です。OSS で完結する読者は Dockerfile + K8s マニフェスト、Databricks ユーザは 7.5 節後半の Databricks Agent Framework が中心になります。
- 7.6-7.7 節 (ストリーミング、FastAPI ラッパ、Gradio UI) は本書で「サンプルリポジトリに含まれていません」と明記されており、概念紹介として読む箇所です。動かしたい場合は本書のコードをそのまま試せます。
